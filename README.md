# CivicMind

**From complaints to incidents.** An AI-powered civic incident-intelligence platform that fuses scattered citizen complaints into one explainable incident — then investigates, prioritises, plans a response, tracks execution and *verifies* that the real-world problem was solved.

Built for **Build with भारत 4.0** · Team **CodeHigh** (MIT ADT Pune) · Problem statement: *Sustainability & Social Impact*.

---

## How it works (public, citizen-first)

The platform **starts completely empty**. Nothing is pre-loaded.

1. A citizen signs in and submits a report — category, description, location and a **required photo of the issue**.
2. **Sarvam AI** classifies it (category, severity, responsible department) and an **evidence check** verifies the photo is legitimate (not blank, not tiny, not a re-used or duplicate image).
3. The report instantly appears on the **officer dashboard** and the **live map**.
4. When enough nearby, related reports arrive, CivicMind **fuses them into one incident** automatically.
5. The officer opens the incident, reads the **AI investigation**, and **approves / edits / rejects** the response plan.
6. The officer does the work and **must upload a proof-of-resolution photo**, which the AI verifies before the incident can be closed.
7. Resolution is confirmed by comparing **before-and-after** complaint signals, and every affected citizen is notified — **naming the officer who resolved it**.

`Detect → Investigate → Prioritize → Act → Verify`

### Roles & permissions

| Role | Can do | Cannot do |
|---|---|---|
| **Citizen** | File complaints (with photo proof), track them live | Resolve incidents |
| **Officer** | Resolve incidents **and individual complaints** directly — approve plans, execute, and submit AI-verified proof | **File complaints** |
| **Admin** | Oversee everything: all citizen complaints *and* all officer responses/resolutions, manage users | — |

Role rules are enforced on both the client and the server (an officer calling the complaint API gets `403`; visiting the citizen page redirects to the officer dashboard).

### Evidence & verification

- A **citizen photo is mandatory** and is checked before the complaint is accepted — blank/uniform images, tiny files, low-resolution images and re-used images are flagged.
- An **officer proof-of-resolution photo is mandatory** and cannot be the same image as the issue photo. It is verified by the AI before the issue is marked solved.
- Verdicts are shown as **Verified / Needs review / Flagged** with confidence and reasons, and are visible to the admin.

### Resolving — two ways, so an officer can always act

1. **Directly, from the officer dashboard.** Every complaint row has a **Resolve** button. Opening it fetches an **AI-generated resolution plan** — the recommended action, the assigned team, an **estimated resolution time**, and an inspection checklist (generated by Sarvam AI). The officer sees the citizen's issue photo, uploads a proof-of-resolution photo, and submits. The AI verifies the proof and the complaint is marked solved.
2. **At incident level.** When 3+ nearby related reports fuse into an incident, the officer approves the AI response plan (which also carries an estimated time), marks work in progress, then submits proof to close the whole incident.

Both paths notify the affected citizens, naming the officer who resolved the issue.

### Dashboard metrics that move

Resolving an issue immediately updates the officer dashboard: **Open complaints** falls, **Resolved** rises, **Affected citizens** drops, and the **Resolution rate** (resolved ÷ total complaints) increases. The resolution-trend chart's "Resolved" line counts complaints resolved that day, whichever path was used.

## Tech stack

| Layer | Technology |
|---|---|
| Frontend | HTML5 + CSS3 + vanilla JavaScript (no build step) |
| Maps | Leaflet.js + OpenStreetMap |
| Charts | Chart.js |
| Backend | Python + FastAPI |
| Database | SQLite (single file, PostgreSQL-ready schema) |
| AI | **Sarvam AI** Chat Completions (`sarvam-105b`) + deterministic fallback |

Core clustering and priority maths stay deterministic in Python so the system is predictable and demonstrable; Sarvam AI adds classification, investigation narrative, priority rationale and response planning. If the AI is ever unreachable, CivicMind transparently falls back to its rule-based engine — a live demo never breaks.

## Nothing is hardcoded

All domain data lives in **`data/civicmind_config.json`** — edit that file, not the code:

- city name & map centre
- complaint **categories**
- **department** routing
- **wards / zones** (used for area mapping)
- demo accounts
- priority thresholds and clustering radius/time-window

Secrets and environment values live in **`.env`** (gitignored) or real environment variables. The frontend reads categories, wards and the city centre from the API, so the browser has no hardcoded values either.

## Quick start

**Windows** — double-click **`run.bat`**, or in PowerShell:
```powershell
cd backend
python -m pip install -r requirements.txt
python -m uvicorn main:app --reload --port 8000
```

**macOS / Linux:**
```bash
./run.sh
# or: cd backend && python3 -m pip install -r requirements.txt && python3 -m uvicorn main:app --reload --port 8000
```

Then open **http://localhost:8000**.

> **Open it through the server — not by double-clicking the HTML files.** CivicMind is a client–server app: the pages talk to the API, and the styling/scripts live in the `css/` and `js/` folders. Opening `index.html` directly (a `file://` URL) will show a red banner telling you to start the server. Always use `http://localhost:8000`.

> On Windows the command is `python` (or `py`), **not** `python3` — `python3` is a Microsoft Store stub that prints "Python was not found".

### Accounts

Anyone can register as a citizen from the login page. Officer and admin accounts are seeded from the config file:

| Role | Email | Password |
|---|---|---|
| Citizen | `citizen@civicmind.in` | `citizen123` |
| Officer | `officer@civicmind.in` | `officer123` |
| Admin | `admin@civicmind.in` | `admin123` |

The login page has a **single form** (no role selector). Officers/admins simply sign in with their own credentials and land on the right dashboard. The demo credentials are shown on the login page **only while `expose_demo_credentials` is `true`** in the config file — set it to `false` before a real public launch.

## Sarvam AI

The API key is read from `.env` / the environment — it is never hardcoded in source.

```
SARVAM_API_KEY=sk_xxxxxxxx
```

`/api/health` and every AI result report which engine ran (`sarvam` or `rules`).

> **Security:** the `.env` file in this bundle contains a live key. Do not publish the bundle or commit `.env`. Rotate the key at <https://dashboard.sarvam.ai> if it has been shared, and set it as a host environment variable in production.

| GET | `/api/complaints` · `/api/complaints/{id}` | List / fetch |

## Responsible AI

- AI output is always shown as **reviewable evidence** with confidence language ("probable incident"), never as fact.
- Numeric detection, clustering and priority scoring stay deterministic in Python.
- Passwords are stored as PBKDF2 hashes; tokens are HMAC-signed; the signing secret is auto-generated if not supplied.
- The API key is never committed to source.
